# Форматы бинарных логов

Чтобы использовать `T-Hist` вместе с мейлерами, которые он не поддерживает, необходимо сконвертировать логи мейлеров в один из форматов, понимаемых `T-Hist`.
В данном документе рассмотрены следующие форматы:

  - формат бинарного лога `Binkd`, он же формат `T-Mail` до версии 2603 (старый формат `T-Mail`);
  - формат бинарного лога `T-Mail` версий 2603 и новее (новый формат `T-Mail`);
  - три версии собственного формата `T-Hist` c 64-битными значениями трафика, возможностью сохранения нескольких текстовых строк и другими преимуществами.

## Бинарный лог Binkd (лог T-Mail старого формата)

Файл бинарного лога `Binkd` состоит из записей длиной 28 байт. Сигнатура в начале файла отсутствует.
Каждая запись имеет следующую структуру:

```C
struct {
    u16    fZone;      // номер зоны FTN-адреса
    u16    fNet;       // номер сети FTN-адреса
    u16    fNode;      // номер узла FTN-адреса
    u16    fPoint;     // номер пойнта FTN-адреса
    u32    fSTime;     // Unix-время начала сессии
    u32    fLTime;     // длительность сессии в секундах
    u32    fBReceive;  // количество принятых байт
    u32    fBSent;     // количество отправленных байт
    u8     fFReceive;  // количество принятых файлов (не используется в T-Hist)
    u8     fFSent;     // количество отправленных файлов (не используется в T-Hist)
    u16    fStatus;    // статус сессии
} TS;

// Типы данных: 
//  u8  - unsigned char 8 bit
//  u16 - unsigned int 16 bit
//  u32 - unsigned int 32 bit

// Статус сессии fStatus - целое число:
//   1 - успешно завершившаяся исходящая сессия
//   2 - успешно завершившаяся входящая сессия
//   3 - любая завершившаяся с ошибкой сессия (например, оборванная)
```

Описание структуры бинарного лога взято из репозитория `Binkd` на [GitHub](https://github.com/pgul/binkd),
файл https://github.com/pgul/binkd/blob/master/binlog.c

Cтатус сессии в старом формате не содержит информации о том, была ли сессия защищена паролем или нет.
Поэтом при обработке бинарных логов старого формата `T-Hist` не генерирует статистику по парольным и непарольным сессиям.

Ниже приведён пример дампа файла бинарного лога `Binkd`, содержащего одну запись длиной 28 байт с информацией о сессии c узлом 2:5020/378.0,
начавшейся 2026-08-06 23:06:43, длившейся 1 секунду, за время которой было отправлено 6788 байт одним файлом.
Сессия была входящая и завершилась нормально.

```
0000000000: 02 00 9C 13 7A 01 00 00 │ 83 13 75 6A 01 00 00 00  ....z.....uj....
0000000010: 00 00 00 00 84 1A 00 00 │ 00 01 02 00              ............
```

Указанное в статусе направление сессии (входящая или исходящая) у `Binkd` противоположно тому, как указывает направление `T-Mail`.
Поэтому при обработке бинарного лога `Binkd` в конфигурационном файле необходимо использовать параметр `SwapInOut Yes`.
Если при конвертации в бинарный лог записывать статус сессии так:

```C
// Статус сессии fStatus - целое число:
//   1 - успешно завершившаяся входящая сессия
//   2 - успешно завершившаяся исходящая сессия
//   3 - любая завершившаяся с ошибкой сессия (например, оборванная)
```

то параметр `SwapInOut Yes` не нужен.

## Бинарный лог T-Mail нового формата

Бинарный лог `T-Mail` нового формата содержит больше информации о сессии, чем бинарный лог старого формата. В частности, в логе сохраняется признак,
была ли сессия защищена паролем или нет, что позволяет `T-Hist` генерировать статистику по парольным и непарольным сессиям. Также в логе корректно
отмечаются нормально завершившиеся сессии и оборванные сессии. И, наконец, в бинарном логе может быть сохранена текстовая информация,
которую `T-Hist` может отобразить в режиме широкого экрана.

Первые два байта файла бинарного лога `T-Mail` нового формата содержат сигнатуру `0x00F1` (побайтово: `0xF1`, `0x00`).
Далее идут записи длиной 100 байт. Каждая запись имеет следующую структуру:

```C
struct {
    u16    fZone;      // номер зоны FTN-адреса
    u16    fNet;       // номер сети FTN-адреса
    u16    fNode;      // номер узла FTN-адреса
    u16    fPoint;     // номер пойнта FTN-адреса
    u32    fSTime;     // Unix-время начала сессии
    u32    fLTime;     // длительность сессии в секундах
    u32    fBReceive;  // количество принятых байт
    u32    fBSent;     // количество отправленных байт
    u8     fFReceive;  // количество принятых файлов (не используется в T-Hist)
    u8     fFSent;     // количество отправленных файлов (не используется в T-Hist)
    u16    fStatus;    // статус сессии
    u8     unused[8];  // не используется в T-Hist
    u8     fNamelen;   // длина строки, находящейся в следующих байтах (не более 63)
                       // либо 0, если запись не содержит текстовую информацию
    char   sName[63];  // массив, содержащий строку с информацией о FTN-системе
                       // или с другой текстовой информацией
} TMailLogRecord;

// Типы данных: 
//  u8  - unsigned char 8 bit
//  u16 - unsigned int 16 bit
//  u32 - unsigned int 32 bit

// Статус сессии fStatus - набор битов:
//  Bit 0 - установлен в случае входящей сессии
//  Bit 1 - установлен в случае исходящей сессии
//  Bit 2 - установлен, если сессия завершилась нормально
//          (не была оборвана, не произошло других ошибок)
//  Bit 3 - установлен, если сессия была защищена паролем
```

`T-Hist` рассматривает данный формат более расширенно, чем `T-Mail`. Сам `T-Mail`, сохраняя в бинарном логе записи длиной 100 байт,
не использует последние 64 байта и не записывает текстовые строки. Поэтому можно, сохраняя совместимость с `T-Mail`, задействовать
неиспользуемые байты для хранения дополнительных данных (например, текстовой строки с информацией о FTN-системе).

Ниже приведён пример дампа файла бинарного лога `T-Mail` нового формата, содержащего одну запись. В начале файла находится двухбайтовая
сигнатура `0x00F1`. Далее идёт запись длиной 100 байт с информацией о сессии c узлом 2:5020/378.0, начавшейся 2026-09-07 00:07:35,
длившейся 1 секунду, за время которой было отправлено 31628 байт одним файлом. Сессия была входящая, защищённая паролем, и завершилась нормально.
Запись также содержит текстовую строку длиной 34 символа с IP-адресом, именем FTN-системы и её локацией.

```
0000000000: F1 00 02 00 9C 13 7A 01 │ 00 00 47 00 9E 6A 01 00  ......z...G..j..
0000000010: 00 00 00 00 00 00 8C 7B │ 00 00 00 01 0D 00 00 00  .......{........
0000000020: 00 00 00 00 00 00 22 39 │ 32 2E 33 36 2E 33 37 2E  ......"92.36.37.
0000000030: 32 30 39 3B 20 6B 6C 75 │ 67 3B 20 4D 6F 73 63 6F  209; klug; Mosco
```

## Собственные форматы T-Hist

Недостатком форматов бинарных логов всех мейлеров, поддерживаемых старой версией `T-Hist`, является использование 32-битных величин для записи
информации о количестве отправленных и полученных байт. В таких бинарных логах невозможно корректно сохранить информацию о трафике,
если во время сессии было отправлено или получено более 4 гигабайт.

Форматы бинарных логов мейлеров разрабатывались в эпоху dial-up, когда передать более 4 гигабайт за одну сессию было практически нереально.
Но в эпоху Fido-over-IP и высокоскоростных сетей сессия с трафиком более 4 гигабайт – обычное явление, особенно на крупных раздающих хабах.

Анализ исходного кода `Binkd` в репозитории на [GitHub](https://github.com/pgul/binkd) показывает, что 64-битные версии `Binkd` выполняют
обработку данных о трафике с помощью 64-битных переменных. Но при записи в бинарный лог `Binkd` вынужден принимать ограничения 32-битного формата
и отбрасывать старшие байты. 

Поэтому разработка и использование новых форматов бинарных логов с 64-битными значениями трафика является актуальной задачей.

В `T-Hist` реализована поддержка нескольких версий собственного формата бинарных логов с 64-битными значениями трафика. Разработчикам FTN-мейлеров
предлагается использовать бинарные логи собственного формата `T-Hist` в своих программных продуктах. Помимо корректного сохранения данных о сессиях
с большими объёмами трафика, формат позволяет сохранять текстовые строки, которые `T-Hist` может выводить в режиме широкого экрана.
Также формат `T-Hist` позволяет записывать в бинарный лог отметку `Listed` для сессий, FTN-адреса которых заданы в конфигурационных файлах мейлера
или присутствуют в нодлистах, указанных в конфигурации мейлера.

### Версия 1 собственного формата T-Hist

Поддерживается, начиная с версии `T-Hist` `1.4.0`.

Первые 5 байт бинарного лога первой версии формата `T-Hist` содержат сигнатуру, состоящую из четырёх символов `H`, `I`, `S`, `T` и одного байта
с номером версии формата. Сигнатура в виде последовательности шестнадцатиричных значений: `0x48`, `0x49`, `0x53`, `0x54`, `0x01`.
  
Далее идут записи длиной 256 байт. Каждая запись имеет следующую структуру:

```C
struct {
    uint16_t  Zone;         // номер зоны FTN-адреса
    uint16_t  Net;          // номер сети FTN-адреса
    uint16_t  Node;         // номер узла FTN-адреса
    uint16_t  Point;        // номер пойнта FTN-адреса
    uint64_t  SessionStart; // Unix-время начала сессии
    uint64_t  BytesRcv;     // количество принятых байт
    uint64_t  BytesSnt;     // количество отправленных байт
    uint32_t  FilesRcv;     // количество принятых файлов (не используется в T-Hist)
    uint32_t  FilesSnt;     // количество отправленных файлов (не используется в T-Hist)
    uint32_t  SessionTime;  // длительность сессии в секундах
    uint16_t  Status;       // статус сессии
    uint8_t   Index[4];     // массив индексов строки
    char      Strings[206]; // массив, содержащий строки
} THistLogRecord;

// Типы данных: 
//  uint8_t  - unsigned char 8 bit
//  uint16_t - unsigned int 16 bit
//  uint32_t - unsigned int 32 bit
//  uint64_t - unsigned int 64 bit

// Статус сессии Status - набор битов:
//  Bit 0 - установлен, если сессия была входящей
//  Bit 1 - установлен, если сессия была исходящей
//  Bit 2 - установлен, если сессия завершилась нормально
//          (не была оборвана, не произошло других ошибок)
//  Bit 3 - установлен, если сессия была защищена паролем
//  Bit 4 - установлен, если адрес Listed (присутствует в нодлистах,
//          указанных в конфигурации мейлера)

// Массивы Index и Strings позволяют сохранить в записи до 5
// null-terminated строк, занимающих в сумме не более 206 байт
//  строка 0 - начинается со Strings[0]
//  строка 1 - начинается со Strings[Index[0]] если Index[0] < 206, иначе отсутствует
//  строка 2 - начинается со Strings[Index[1]] если Index[1] < 206, иначе отсутствует
//  строка 3 - начинается со Strings[Index[2]] если Index[2] < 206, иначе отсутствует
//  строка 4 - начинается со Strings[Index[3]] если Index[3] < 206, иначе отсутствует
```
 
В строках можно сохранять текстовую информацию о FTN-системе, получаемую во время сессии. Например, в строке 0 – IP-адрес,
в строке 1 – доменное имя, в строке 2 – имя FTN-системы, в строке 3 – локацию FTN-системы, в строке 4 – имя сисопа.

### Версия 2 собственного формата T-Hist

Поддерживается, начиная с версии `T-Hist` `1.5.0`.

Вторая версия собственного формата `T-Hist`, обладая всеми достоинствами первой версии, позволяет заметно уменьшить размер файла бинарного лога
благодаря записям переменной длины.

Первые 5 байт бинарного лога второй версии формата `T-Hist` содержат сигнатуру, состоящую из четырёх символов `H`, `I`, `S`, `T` и одного байта
с номером версии формата. Сигнатура в виде последовательности шестнадцатиричных значений: `0x48`, `0x49`, `0x53`, `0x54`, `0x02`.
  
Затем идут записи переменной длины, но не более 256 байт каждая. Каждая запись начинается с байта, содержащего её длину (без учёта самого этого байта).
Далее расположены поля записи в том же порядке, как у записей первой версии формата. Алгоритм построения записи второй версии формата следующий:

  1. Обнуляем 256-байтный буфер.
  ```C
  uint8_t* buffer[256];
  memset(buffer, 0, 256);
  ```
  2. Байт по индексу 0 пока не трогаем, а начиная с байта по индексу 1 cоздаём в этом буфере запись, структура которой описана в первой версии формата, с единственным
  отличием: массив строк `Strings` имеет размер 205 байт, а не 206.
  ```C
  struct THistLogRecord* pRecord = (struct THistLogRecord*)&buffer[1];
  /* заполняем поля записи, например:
  pRecord->Zone  = 2;
  pRecord->Net   = 5020;
  pRecord->Node  = 378;
  pRecord->Point = 0;
  ...
  */
  ```
  3. Определяем индекс последнего ненулевого байта - это будет длина записи - и помещаем его в буфер по индексу 0:
  ```C
  uint8_t len = 255;
  while( (len > 1) && (buffer[len] == 0) ) len--;
  buffer[0] = len;
  ```
  4. Записываем в файл бинарного лога `len + 1` байт, начиная с адреса `buffer`.

При чтении записей из бинарного лога сначала читается один байт длины записи `len`, а затем в предварительно обнулённый буфер читаются `len` байт самой записи.

### Версия 3 собственного формата T-Hist

Поддерживается, начиная с версии `T-Hist` `1.7.0`.

Третья версия собственного формата `T-Hist`, обладая всеми достоинствами второй версии, позволяет осуществлять проверку целостности бинарного лога благодаря наличию
у каждой записи контрольной суммы. Это позволяет исправить ситуации, когда предыдущая запись была сохранена мейлером в бинарный лог не полностью из-за сбоя программы
или по какой-либо другой причине. При следующем запуске мейлер может проверить последнюю запись в логе, и если она некорректна, то удалить её, перейдя к последней
корректной записи. А `T-Hist`, обрабатывая бинарные логи третьей версии формата, корректно пропускает битые записи даже если они находятся в середине файла.

Структура записи третьей версии формата и алгоритм подсчёта контрольных сумм предложены Alexey Matrosov `2:203/910`, разработчиком форка мейлера qico
(см. на [GitHub](https://github.com/glasslike/qico)), использующего, начиная с версии 0.60.2, бинарный лог третьей версии формата `T-Hist`.

Первые 5 байт бинарного лога третьей версии формата `T-Hist` содержат сигнатуру, состоящую из четырёх символов `H`, `I`, `S`, `T` и одного байта
с номером версии формата. Сигнатура в виде последовательности шестнадцатиричных значений: `0x48`, `0x49`, `0x53`, `0x54`, `0x03`.

Далее идут записи переменной длины, но не более 261 байт каждая. Записи третьей версии формата получаются из записей второй версии дописыванием дополнительных 5 байт:
- 4 байта контрольной суммы;
- 1 байт, повторяющий начальный байт записи (её длину).

Для вычисления контрольной суммы используется алгоритм `CRC-32/ISO-HDLC`. В программах на C/C++ можно использовать библиотечную функцию `crc32()` библиотеки `zlib`.

Алгоритм построения записи третьей версии формата следующий:

  1. Обнуляем 261-байтный буфер.
  ```C
  uint8_t* buffer[261];
  memset(buffer, 0, 261);
  ```
  2. Создаём в этом буфере запись в точности по алгоритму для второй версии формата без каких либо изменений. В результате этого `buffer[0]` будет содержать длину записи,
а начиная с `buffer[1]` будут располагаться поля записи с последним ненулевым байтом `buffer[bufer[0]]`:
  ```C
  struct THistLogRecord* pRecord = (struct THistLogRecord*)&buffer[1];
  /* заполняем поля записи, например:
  pRecord->Zone  = 2;
  pRecord->Net   = 5020;
  pRecord->Node  = 378;
  pRecord->Point = 0;
  ...
  */
  uint8_t len = 255;
  while( (len > 1) && (buffer[len] == 0) ) len--;
  buffer[0] = len;
  ```
  3. Считаем по алгоритму `CRC-32/ISO-HDLC` контрольную сумму участка памяти от начала массива `buffer` длиной `len + 1` байт (то есть контрольную сумму всей записи,
включая начальный байт её длины). При использовании библиотеки `zlib` это можно сделать так:
  ```C
  uLong crc = crc32(0L, Z_NULL, 0); 
  crc = crc32(crc, buffer, len + 1);
  ```
  4. Сохраняем 4 байта контрольной суммы в массив `buffer`, начиная с индекса `len + 1`. А в байте с индексом `len + 5` повторяем значение длины записи `len`.
  ```C
  memcpy(&buffer[len + 1], &crc, 4);
  buffer[len + 5] = len;
  ```
  5. Записываем в файл бинарного лога `len + 6` байт, начиная с адреса `buffer`.

Чтение записей из бинарного лога третьей версии формата выполняется следующим образом:

  1. Читаем один байт длины записи `len` и сохраняем его в `buffer[0]`.
  2. Читаем `len + 5` байт и сохранем их, начиная с `buffer[1]`.
  3. Сравниваем `buffer[0]` и `buffer[len + 5]`. Если они не совпали, то запись считается битой по причине несовпадения значений длины в начале и в конце.
  4. Вычисляем контрольную сумму от начала массива `buffer` длиной `len + 1` байт. Если она не совпала с 4 байтами контрольной суммы, расположенными начиная
с `buffer[len + 1]`, то запись считается битой по причине несовпадения контрольной суммы.
  5. Если совпали и байты длины, и контрольная сумма, то обнуляем `buffer[len + 1]` и обрабатываем запись. (Обнуление байта нужно для корректной обработки строк.)

Наличие байта с длиной записи не только в начале, но и в конце записи, позволяет просматривать бинарный лог как от начала к концу, так и от конца к началу.
